# Feature Implementation Spec: Homeowner works with style-blended Simulations across every kitchen photo

## Source Feature

- `id`: simulations-ux-overhaul (issue #29)
- `area`: ux-simulations
- `depends_on`: controlnet-render (accepted), budget-tier-computation (accepted)
- `status`: not_started at planning time (2026-11-14); set to `in_progress` by the planner
- `source`: `feature_list.json`; branch `feature/simulations-ux-overhaul`
- Developer decisions in the feature notes are settled. This is one feature by developer decision, but it is far over the 250-line target and the single-data-model rule. See "Phasing".

## Goal

Pressing Generate creates a **Simulation**: one Render per kitchen photo (up to 8), all sharing one **calculated style** that blends the common traits of every Style Gallery pick and every Moodboard reference. Each "Generate again" recalculates the style with new random weights and creates a new Simulation. Results groups Renders by Simulation. The project page gains "My simulations" (open, select, delete). A Budget belongs to the selected Simulation and is built from the elements a vision model sees in all its images, with Luxury > High > Medium > Low enforced in code (ADR 0002 unchanged). Plus UX fixes: slider position persists, responsive picker/history, cm default, wrapping Style Gallery chips.

## Non-Goals

- Admin UI for the blend mode (`admin-service-endpoints` adds it), per-user quotas (`daily-quota-enforcement`), Persona chat, Dossier, DIY PDF, decluttering inpainting.
- Cancellation of a running Simulation, a durable GPU queue, SSE (polling stays), cloud fallback.
- Marking a Simulation "stale" after the project is edited, comparing Simulations side by side.
- Deleting the old text model from the `bricomission_llm-models` volume (manual, after acceptance). Never delete model volumes.

## Phasing (one branch, one PR, nothing committed until accepted)

Phases are ordered; each task below is single-session sized and phase N+1 may not start before phase N is green.
A: spikes (vision model, IP-Adapter, residency). B: data model, Simulation API, calculated style. C: Budget per Simulation, inventory, ordering. D: owner edit routes and platform setting. E: web (blocked until the design read-back exists). F: docs, E2E, real-GPU smoke.
If phase A shows IP-Adapter or the vision model cannot work, stop and report: the orchestrator decides (see OQ-2) before any other phase starts.

## Decisions

1. **Calculated style** (new ADR 0005). Pure module `calculated-style.ts`. Inputs: Moodboard items (gallery id or upload id), mode, `styleSeed`, `isFirst`.
   - Weights: the first Simulation of a project (no Simulation exists at creation) uses equal weights `1/n`. "Generate again" draws `raw_i` uniform in [0.5, 1.5] from a seeded PRNG (mulberry32 over `styleSeed`), divides by the mean, clamps to [0.5, 1.5], normalizes to sum 1. Bounds: max/min weight <= 3. Same seed gives the same weights. `styleSeed` is `crypto.randomInt(0, 2**31)`, stored on the Simulation, never returned.
   - Render seed = `hash(styleSeed, photoPosition)`: reproducible, differs per photo.
   - Gallery references use the committed JPEGs in `apps/api/assets/style-gallery/<id>/full.jpg`; uploads use their `full` object. All are scaled to <= 768 px longest edge before they leave the API.
2. **Blend modes** `ip_adapter | vlm_text | both`, stored in new table `platform_setting` (`key` text PK, `value` jsonb, `updated_at`, `updated_by`), key `style_blend_mode`. Read at Simulation creation and copied to `simulation.blend_mode`. Safe default when the row is missing or invalid: `vlm_text` (needs no new ComfyUI node and no extra VRAM). The spike may flip the default constant to `both`. Admin API now: `GET/PUT /admin/settings/style-blend` in `AdminController` (`@Roles('admin')`, body `{ mode }`, 400 on any other value, never `@Public()`).
   - `ip_adapter`: prompt text = existing dominant-style text; references go to IP-Adapter at their weights.
   - `vlm_text`: prompt text = merged traits, no IP-Adapter nodes.
   - `both`: merged traits text + IP-Adapter at a reduced base weight.
3. **VLM description and merge.** Each reference is described once by the vision model (JSON schema: `palette[]`, `materials[]`, `cabinetStyle`, `lighting`, `keywords[]`, each field short). Descriptions are cached in table `reference_style_trait` keyed by `(sha256 of the scaled JPEG, model id)`, so "Generate again" needs no new GPU work. The **merge is code, not an LLM call**: terms are scored by the sum of the weights of the references that mention them; the top terms (ties by seed) fill a style text of <= 160 characters (fits one 75-token CLIP chunk with the existing prefix and suffix). The fixed prompt prefix and negative prompt of `render-prompt.ts` stay. If the vision job fails the Simulation does not fail: it falls back to the dominant-style text, `style_degraded = true` is stored and the UI shows a quiet note.
4. **IP-Adapter in ComfyUI.** `ComfyUI_IPAdapter_plus` (custom node, pinned commit in `infra/comfyui/Dockerfile`, `ARG IPADAPTER_PLUS_SHA`), `ip-adapter-plus_sdxl_vit-h.safetensors` in `models/ipadapter/`, CLIP ViT-H image encoder in `models/clip_vision/`, fetched by `ai-fetch` with pinned commit and expected bytes (record sizes in the spike). Workflow: one `IPAdapterEncoder` per reference with weight `min(1, base * n * w_i)`, merged with `IPAdapterCombineEmbeds`, applied with `IPAdapterEmbeds` on the checkpoint model, next to the existing ControlNet chain (canny + depth assist unchanged). The combine node takes 5 inputs: the spike must prove chaining for up to 12 references; fallback: the 5 highest weights go to IP-Adapter (ties by position) and the rest only reach the prompt through the VLM text. Offline after fetch (`HF_HUB_OFFLINE=1`).
5. **Multimodal LLM** (ADR 0001 amended, no rewrite). `Qwen3-VL-30B-A3B-Instruct` GGUF (Q4_K_M) plus its `mmproj` file (F16 or Q8_0, chosen in the spike) in `llm-models`, fetched by `ai-fetch`. `llama-server` gets `-m <new gguf> --mmproj <file> --jinja`, still `--n-cpu-moe`. `LlmMessage.content` becomes `string | LlmContentPart[]` (`{type:'text'}` | `{type:'image', data: Buffer, mime}`); `LlamaServerLlmAdapter` sends images as `image_url` data URIs. `LlmRequest` gains `task?: 'budget' | 'inventory' | 'style_traits'` (fake adapter dispatch). Vision calls are `broker.submit('llm', ...)` jobs. Image inputs <= 768 px long edge to bound prompt tokens (about 430 tokens each); `--image-max-tokens` and `--no-mmproj-offload` are measured fallbacks. Check `LLAMA_CTX_SIZE` (16384) against 8 images + 30 chunks and raise it only if the measurement says so.
6. **Residency (decide by measurement, task A3).** Baseline 2026-11-14 (text LLM resident 2.9 GB): idle both 8.6 GB, render peak max 16,217 of 16,304 MiB. IP-Adapter adds about 1.5-2 GB while rendering and the vision model about 1 GB, so co-residency is expected to fail for `ip_adapter`/`both`. Rule: if the measured render peak with the LLM resident exceeds 15,600 MiB, or any OOM or >25 % slowdown occurs, `GpuResidencyHook` unloads. `afterImage`/`beforeImage` stay; add `beforeLlm()` (ComfyUI `POST /free` with `unload_models` and `free_memory`) and `afterLlm()` no-op, and make `beforeImage()` unload the LLM. LLM unload mechanism is a spike result, in this order of preference: llama-server router-mode `POST /models/unload` and reload on the next request; `--sleep-idle-seconds` with `beforeImage` polling `/props` until sleeping; last resort a stop/start helper (no docker socket in the API: needs a written justification). Switching cost is paid once per Simulation (vision describe, then N renders back to back) and once per Budget (inventory, then pricing). The hook call from the broker for `llm` jobs is the only broker change; scheduling rules stay.
7. **Simulation model.** One Simulation = one group of Renders from one calculated style. At most one active (queued/running) Simulation per project (409 `simulation_in_progress`); no per-project cap (developer decision; replaces `RENDER_MAX_PER_PROJECT`). Max photos per Simulation = the existing 8-photo project cap (8 renders about 90 s plus vision). The orchestration is a `SimulationRunner`: POST creates the Simulation and N queued Renders, answers 202; stage `describing` (one `llm` job, skipped for `ip_adapter` and when all references are cached), then stage `rendering`: one `image` job per Render, **submitted one after the other** (the next after the previous finishes) so N jobs never hit `maxQueued` and "n of N" is exact. Progress: `{ stage, total, succeeded, failed, current }`.
8. **Partial failure (OQ-3, recommended).** Successful Renders stay visible; each failed Render shows Retry (`POST .../renders/:id/retry`: same row, same style and seed, `attempts + 1`). A Simulation is **selectable and budget-eligible only when every Render succeeded** (a Budget "from all images" would silently skip an angle). A partly failed Simulation can be retried or deleted. A retry counts as one unit for quotas.
9. **Selection.** At most one selected Simulation per project (partial unique index). `PUT /kitchen-projects/:id/selected-simulation {simulationId|null}`. Deleting the selected one clears the selection.
10. **Budget per Simulation (developer decision c).** `budget.simulation_id` NOT NULL FK cascade. Invariants by partial unique indexes: at most one `succeeded` and at most one active Budget per Simulation; failed rows are deleted when the next compute starts. A recompute keeps the old Budget visible until the new one succeeds; the success transaction deletes the old one. `BUDGET_MAX_PER_PROJECT`, `budget_limit_reached` and `maxBudgets` are removed. `POST /kitchen-projects/:id/budget` keeps its path and guards and computes for the selected Simulation: 409 `no_simulation_selected`, 409 `simulation_not_ready`.
11. **Element inventory.** Per Render, a vision call over its `full` image (schema: `elements[]` of `{category enum, label <= 40, count 0-20}`, category list fixed: base/wall/tall cabinet, worktop, sink, tap, hob, oven, hood, fridge, dishwasher, backsplash, flooring, lighting, island, other). Cached on `kitchen_render.inventory` (jsonb) so recompute reuses it. Code merges across images: per category the **max** count (the same cabinet seen from two angles is not doubled), up to 3 labels. The merged inventory feeds the prompt and extends retrieval queries (fixed 8 plus one per present category, at most 12). Counts are quantities, never amounts. Inventory jobs are separate `llm` broker jobs (about 10 s each) so the budget job stays inside its timeout; progress "n of N images".
12. **Tier ordering enforced in code.** (a) Retrieval keeps hits grouped by category query; pure `price-bands.ts` parses each SKU line's price and assigns terciles per category (`premium|mid|basic`; fewer than 3 candidates: no bands). The prompt lists the band per SKU and tells the model to take Luxury from premium, Low from basic. (b) After extraction and math, pure `isStrictlyOrdered(totals)` requires `luxury > high > medium > low` on `totalCents` (equal fails). If violated the attempt is rejected, the feedback message names the totals and the rule, and the next attempt runs. `BUDGET_MAX_ATTEMPTS` default 3. After the last attempt still out of order (developer decision 2026-11-14, OQ-5): pure `relabelByTotal` ranks the four verified tiers by `totalCents` descending and assigns the names Luxury, High, Medium, Low in that order, sets `budget.relabeled = true` (new boolean column, default false) and the Budget succeeds; the relabel changes only names, never an amount, price or Line Item. If two totals are equal even after ranking, the Budget fails with `verification_failed`. The Budget screen shows a quiet note when `relabeled` is true (design must cover it) and the tier order is unit-tested for both paths. `GPU_BROKER_LLM_TIMEOUT_MS` default becomes 240000 (3 attempts at about 55 s).
13. **Existing dev data.** Recommended: migrate, do not delete. SQL only: each existing `kitchen_render` becomes its own one-Render Simulation (ordinal by `created_at`, `style_weights` null, `blend_mode` `vlm_text`, `style_degraded` true), so MinIO objects stay owned and a later Delete cleans them. Per project the newest succeeded Budget attaches to the Simulation of the newest succeeded Render; other Budgets are deleted (rows only). No MinIO deletion in SQL.
14. **Claimed projects become editable** (developer: photos, measurements and styles stay editable from the project page). Owner routes mirror the draft routes (same bodies, limits, errors): `POST/DELETE /kitchen-projects/:id/photos...`, `PUT .../measurements`, `POST/DELETE .../moodboard/items...`. They reuse the draft services behind an owner resolver and are refused with 409 `simulation_in_progress` while a Simulation is active. The status CHECKs and repository filters that make claimed rows immutable are relaxed for these routes only. Editing never touches existing Simulations (their Renders keep `photo_id SET NULL` and their own `before` objects).
15. **Quotas.** One Simulation = N Renders = N units. The check belongs in `SimulationsService.create` before any row (`daily-quota-enforcement` plugs in there); the data supports it (`render` rows with `created_at`, `attempts`). Not implemented here.

## Job Story

When I give several photos and a mood, I want every angle of my kitchen renovated in one consistent style, to try other variations and then pick one to price, so I can see and cost one coherent design.

## Users And Permissions

Same as Renders and Budgets: Homeowner owner only; others 404; Professional/Admin 403; anonymous 401; drafts 404 (`OwnedProjectGuard`). Only the setting routes are `@Roles('admin')`. Responses never include seeds, prompts, descriptions, inventory JSON, job ids or backend bodies.

## API Contract

- `POST /kitchen-projects/:projectId/simulations` (empty body). Order: 401/403, 400 id, 404, 409 `project_incomplete`, 409 `simulation_in_progress`, 429 `gpu_queue_full`, 503 `storage_unavailable`. 202 `{ simulation: SimulationView }`.
- `GET .../simulations` -> `{ simulations: SimulationView[] }` newest first. `GET .../simulations/:simulationId` -> `SimulationView`. `DELETE .../simulations/:simulationId` -> 204; 409 `simulation_in_progress`; objects first (503 keeps rows), then the row (Renders and Budget cascade).
- `PUT .../selected-simulation` `{ simulationId: uuid | null }` -> 200 `{ selectedSimulationId }`; 404 foreign id, 409 `simulation_not_ready`.
- `POST .../renders/:renderId/retry` -> 202 `{ simulation }`; 409 `render_not_failed`, `simulation_in_progress`.
- Kept: `GET .../renders/:renderId` and `.../content?variant=before|full|thumb`. **Removed:** `POST .../renders` and `GET .../renders` (the only consumer is the web).
- `SimulationView` = `{ id, ordinal, createdAt, status: 'active'|'succeeded'|'partial'|'failed', stage: 'describing'|'rendering'|'finished', progress: { total, succeeded, failed, current }, selected, blendMode, styleDegraded, style: { keywords: string[], references: { kind: 'gallery'|'upload', refId, weightPercent }[] }, renders: RenderView[], budget: { id, status } | null }`. `RenderView` loses `styleId`, gains `simulationId`, `photoPosition`, `attempts`; `position` stays the queue position.
- Budget: `POST /budget` 202 / the codes above; `GET /budgets` -> `{ budgets: BudgetView[] }` (current plus active, max 2); `BudgetView` gains `simulationId`, `stage: 'inventory'|'pricing'`, `progress { total, done }`; new `BudgetErrorCode` none beyond existing. New `KitchenProjectErrorCode`: `simulation_in_progress`, `simulation_not_ready`, `no_simulation_selected`, `render_not_failed`. Remove `render_limit_reached`, `budget_limit_reached`.
- Admin: `GET/PUT /admin/settings/style-blend`.
- Then `pnpm --filter @bricomission/api openapi:export`; commit `openapi.json` and `schema.ts`. Non-additive (routes removed): list in the PR.

## Acceptance Scenarios

1. **Simulation, fake adapters.** Project with 3 photos and 2 Moodboard items: POST 202; stage `describing` then `rendering` with `progress.current` 1..3; final status `succeeded`, 3 Renders (one per photo, `photoPosition` 0..2), all with `before/full/thumb` objects, same `styleSeed`. First Simulation weights equal; the second POST gives different weights (bounds hold, reproducible from the stored seed).
2. **Guards.** Anonymous 401, Professional 403, foreign Homeowner 404, draft 404; second POST while active 409; delete while active 409; not ready 409 and the broker is never called.
3. **Partial failure.** Scripted image adapter fails photo 2: Simulation `partial`, Renders 1 and 3 readable, Retry on 2 succeeds with the same seed; before the retry `PUT selected-simulation` gives 409 `simulation_not_ready`.
4. **Delete.** Deleting a Simulation with a Budget removes Renders, all MinIO objects of those Renders and the Budget; selection cleared; storage down gives 503 and keeps rows.
5. **Budget.** No selection: 409 `no_simulation_selected`. Selected Simulation: inventory jobs (one per Render) then pricing; Budget shows `simulationId`; recompute keeps the old Budget until the new one succeeds, then only one remains. Scripted adapter returns out-of-order totals (High 500 > Medium 1476 case): attempt rejected, retry with feedback, success; always out of order after 3 attempts: tiers are relabelled by total rank and the Budget succeeds with `relabeled = true` (names only, no amount changes); equal totals even after ranking: `failed` / `verification_failed`. Prices are still verified against chunk text; no amount from the model.
6. **Style modes.** Unit and adapter tests per mode build the expected prompt and workflow (no IP nodes for `vlm_text`; N encoders for `ip_adapter`; both for `both`); missing/invalid setting yields `vlm_text`; admin PUT persists, non-admin 403.
7. **Migration.** A DB with old Renders and Budgets migrates as in Decision 13 (migration spec with inserted rows); CHECKs and the HNSW index intact.
8. **UI (E2E, fake adapters).** See Verification Plan.
9. **Real GPU.** See Verification Plan.
